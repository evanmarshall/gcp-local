# Cloud Tasks (local emulation)

Status: queues and HTTP-target tasks are implemented locally (issue #36, the
first #19 service slice). The provider is shaped to the
`cloudtasks-dispatch-retry` recording (`gcp_validation/cloudtasks.py`); a
fidelity claim needs that scenario to pass against the emulator, and only the
fields the scenario compares are evidence.

## Surface

- REST v2beta3 routes generated by `tools/genapi`: queues
  create/get/list/patch/delete, pause/resume/purge, get/setIamPolicy, tasks
  create/get/list/delete and forced `:run`, locations list.
- Queue documents carry the relative `name`, `rateLimits`, `retryConfig`,
  `state`, `taskTtl`, `tombstoneTtl`, and `type`. `retryConfig` echoes
  maxAttempts, minBackoff, maxBackoff, and maxDoublings with GCP defaults
  (100, 0.100s, 3600s, 16). Rate limits, TTLs, and type are documented
  defaults that the recording compares only by presence. Delete returns `{}`.
- Task creation takes the `{task: {httpRequest}}` envelope, requires an
  existing queue and an absolute http/https URL, decodes the base64 body
  (bounded at 1 MiB), and returns the BASIC view: the body and OIDC token are
  FULL-view fields that need `cloudtasks.tasks.fullView`.

## Dispatch

- The provider owns one background worker per task. Attempts follow the
  queue's retryConfig: minBackoff doubles maxDoublings times, then grows
  linearly, capped at maxBackoff. A paused queue holds its tasks.
- Each completed attempt sets `dispatchCount`, `firstAttempt`, and
  `lastAttempt`; a transport failure reports `responseStatus.code` 2
  (UNKNOWN), a non-2xx response the mapped RPC code.
- A successful task is removed. A task that exhausts maxAttempts is removed
  after a short local retention (3s) so pollers can read its final attempt;
  the retention is a local choice, not a recorded value.
- OIDC: the dispatcher mints a local ID token for the task's service account
  and audience (default: the target URL) as the Cloud Tasks service agent,
  the same contract the Pub/Sub push delivery uses.

## IAM

- Queue and task methods authorize against the queue, so a queue policy
  (for example `roles/cloudtasks.enqueuer`) grants task creation; a missing
  queue authorizes through the project and then reads 404.
- A task with an `oidcToken` requires `iam.serviceAccounts.actAs` on that
  service account before it is stored. An account that is not a declared
  same-project local service account is an explicit gap, not an allow.

## Explicit gaps

App Engine targets, OAuth tokens, `maxRetryDuration`, `updateMask`, and rate
limit enforcement are gaps.
