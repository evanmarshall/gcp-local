# REST and gRPC gateway

The core accepts Storage REST contracts on `127.0.0.1:4566` and Pub/Sub gRPC contracts on `127.0.0.1:4567`. Both enter the same explicit provider registry. There are no built-in service providers yet, so matched operations report `UNIMPLEMENTED`; an SDK connection alone is not a compatibility pass. See [contract regeneration](../api/README.md).

The gateway owns route matching, transport decoding, error serialization, and context propagation. A request carries the method, principal state, caller subject/project when resolved, resource project/location, resource name, trace ID, and cancellation context. Storage bucket/object ownership cannot be inferred from a globally named bucket; that project stays empty until a provider looks up the owner. Caller project and resource project are separate fields. Pub/Sub resource selectors come from the protobuf contract. Valid W3C traceparent IDs propagate; other requests get a random local trace ID, returned as `x-gcp-local-trace-id`.

Providers register individual methods explicitly. A duplicate, misspelled, or wrong-streaming registration fails. The default identity resolver marks absent credentials anonymous and presented bearer tokens unknown; it never grants administrator or authenticated status. #6 supplies identity resolution, and #7/#8 add authorization before effects. Registering a method does not authorize a request.

REST matching uses the escaped URL and unescapes each variable exactly once, preserving object names with slashes, percent signs, or question marks. JSON bodies are bounded to two MiB and must be objects; upload bodies remain streams for the provider/backend. HTTP authorization headers are removed from the provider's transport header copy after identity resolution. Typed gRPC forwarding uses Google's generated messages. Structured gRPC errors map to HTTP JSON status/errors with protobuf details; unexpected Go errors return a generic internal error. Providers remain responsible for service-specific recorded error shapes and precedence.

The initial streaming path is Pub/Sub `StreamingPull`: the gateway reads the first request to establish its resource context, then passes that same message exactly once to the provider. Further bidirectional messages, deadlines, cancellation, and status errors remain on the original stream. Handlers must observe the call context and finish when cancelled. Shutdown drains both listeners under one deadline and forcibly cancels remaining work after that deadline.

Health and diagnostics stay outside provider dispatch and never call a backend. Protocol tests exercise REST decoding, malformed requests, structured errors, typed gRPC calls, bidirectional delivery/acknowledgements, cancellation/deadlines, and graceful/forced runtime shutdown using local stub providers. These are infrastructure tests, not real-GCP parity evidence. No cloud or backend forwarding is implemented by this layer.
