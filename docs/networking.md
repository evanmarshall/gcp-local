# Compute Engine networking and Connectivity Tests (local emulation)

Status: networks, subnetworks, firewall rules, routes, routers, peerings, and
Network Management Connectivity Tests are implemented locally in one in-memory
provider (`internal/providers/compute`). One real-GCP recording,
`vpc-firewall-connectivity` (2026-10-11), covers the VPC control plane and
Connectivity Tests for IP-address endpoints, and the local provider matches it
in comparison mode. Behavior outside that recording is a local model, not a
fidelity claim.

## Surface

- Compute v1 REST routes generated by `tools/genapi`: networks
  (create/get/list/delete, addPeering, removePeering), subnetworks
  (create/get/list/delete, get/setIamPolicy), firewalls (create/get/list/
  update/delete), routes, routers with Cloud NAT entries, and
  `globalOperations.get/list` and `regionOperations.get`.
- Network Management v1 Connectivity Tests:
  `POST /v1/projects/{p}/locations/global/connectivityTests?testId=ID`, `GET`
  and `DELETE .../connectivityTests/ID`, list (`resources`), and
  `POST .../connectivityTests/ID:rerun`. There is no `:run` method; the real
  API has none.
- Regions are placement attributes, not namespaces (the storage precedent):
  every compute resource lives in the project's global scope so network
  references resolve across regions. Projects are isolated from each other.
- Permission plans follow the documented rows (`compute.*` and
  `networkmanagement.connectivitytests.*`), backed by pinned
  `roles/compute.admin`, `roles/compute.networkAdmin`, `roles/compute.viewer`,
  `roles/networkmanagement.admin`, and `roles/networkmanagement.viewer`.
  Compute denials use the compute error body; Network Management denials use
  the standard `PERMISSION_DENIED` envelope.

## Recorded scenario: `vpc-firewall-connectivity`

Produced by `gcp_validation/networking.py` against a sandbox project with no VM
instances. `sh scripts/check_rest_recordings.sh` replays it locally. What it
establishes, and what the provider now does:

- Self-links use `https://www.googleapis.com/compute/v1/...`, and a
  subnetwork's `region` is the region's link.
- Documents carry exactly the recorded field sets. A network has `id`, `name`,
  `kind`, `selfLink`, `selfLinkWithId`, `creationTimestamp`,
  `autoCreateSubnetworks`, `routingConfig` (`routingMode`, plus
  `bgpBestPathSelectionMode: LEGACY`), `networkFirewallPolicyEnforcementOrder`
  (`AFTER_CLASSIC_FIREWALL`), and `description` when one was given; `mtu`,
  `subnetworks`, and `peerings` appear only when set or non-empty. A
  subnetwork adds `allowSubnetCidrRoutesOverlap`, `fingerprint`,
  `privateIpv6GoogleAccess`, `purpose` (`PRIVATE`), and `stackType`
  (`IPV4_ONLY`), with no empty `description` or `secondaryIpRanges`. A
  firewall always has `description` and omits empty `denied`, `targetTags`,
  and ranges.
- Some validation fails asynchronously. An insert of a subnetwork whose range
  overlaps another subnetwork of the network returns 200 and an operation that
  finishes `DONE` with error `INVALID_USAGE`; nothing is created. Deleting a
  network that subnetworks (locally also firewalls, routes, or routers) still
  use returns 200 and an operation `DONE` with
  `RESOURCE_IN_USE_BY_ANOTHER_RESOURCE`; the network is kept. Both operations
  are readable through `regionOperations.get` / `globalOperations.get`.
  Deleting an absent subnetwork, firewall, route, or router returns 404.
- `addPeering` accepts the current body
  `{"networkPeering": {"name", "network", "exchangeSubnetRoutes"}}` with a
  full URL or relative network name, and the legacy top-level
  `{"name", "peerNetwork"}`. The recorded peering fields are rendered
  (`autoCreateRoutes`, `connectionStatus`, `exchangeSubnetRoutes`,
  `export/importCustomRoutes`, `export/importSubnetRoutesWithPublicIp`,
  `name`, `network`, `stackType`, `state`, `stateDetails`, `updateStrategy`).
  The recording read the peering after both directions were added and saw
  `ACTIVE`; locally a peering is `INACTIVE` until the peer network has a
  peering back, matching GCP's documented behavior but not recorded.
  `removePeering {"name"}` removes one side; an unknown name returns 400.
- Connectivity Tests create returns a finished long-running operation
  (`projects/P/locations/global/operations/...`, `done: true`, the test in
  `response`). A test reads back with exactly `createTime`, `destination`,
  `name`, `protocol`, `reachabilityDetails` (`result`, `traces`,
  `verifyTime`), `source`, and `updateTime`; `description` appears when given.
  Delete returns an operation and later reads 404. The result is stored when
  the test is created or rerun; reads do not re-evaluate the topology.

## Analyzer semantics

The analyzer serves both Connectivity Tests and the local
`POST /_local/networking/reachability` surface (verdicts `unknown`, `dropped`,
`unsupported`). It follows the recorded step order for IP-address endpoints:

1. `START_FROM_PRIVATE_NETWORK` from the subnetwork that contains the source
   address (within the source network when the test names one).
2. `APPLY_EGRESS_FIREWALL_RULE`: the highest-priority enabled EGRESS rule of
   the source network that matches the destination, protocol, and port (deny
   wins at equal priority), or the implied `default-allow-egress` rule.
3. `APPLY_ROUTE`, then a final state.

Recorded outcomes (no VM instances exist in the recording):

- A destination inside a subnetwork of the source network is `UNDETERMINED`
  with `ABORT` cause `UNKNOWN_IP`, whatever the ingress rules say, because no
  endpoint owns the address. The recording shows this for both an allowed and
  a blocked port.
- A private destination outside the source network's subnetworks follows the
  default route and is `UNREACHABLE` with `DROP` cause
  `PRIVATE_TRAFFIC_TO_INTERNET`. GCP returned this for an address in another
  network both without peering and immediately after peering both directions.
  The provider reproduces that observation and does not apply peering routes;
  the recording does not show whether GCP's answer changes later.

Local model, not recorded: an egress deny rule ends with `DROP` cause
`FIREWALL_RULE` (`UNREACHABLE`).

The analyzer never reports `REACHABLE`. These flows are coverage gaps instead
of verdicts. Connectivity Tests create/rerun returns 501 and the local surface
returns `unsupported`:

- a source address outside every modeled subnetwork of the source network;
- a destination matched by an untagged static route (next hops are not
  modeled);
- public destinations, including Cloud NAT egress; routers and NAT
  configuration are stored but not analyzed;
- cross-project endpoints and cross-project peering.

## Explicit gaps

- No VM instances, internal load balancers, or other endpoints: every
  destination address is unknown, so ingress firewall rules, network tags,
  and service accounts never decide a verdict.
- Peering routes, custom-route next hops, Cloud NAT, PSA/PSC, Cloud SQL, and
  hierarchical or network firewall policies are not analyzed.
- Network Management `operations.get` is not routed; create, rerun, and delete
  return already-finished operations.
- The auto-created default route is implied by the analyzer and not listed by
  `routes.list`.
- No persistence across restarts.
